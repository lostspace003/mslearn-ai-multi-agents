# Lab 09 design review: reflect on the release design

1. **Why is a logical semantic version insufficient?** `scanner 1.2.1` describes source compatibility (contracts, dependency ranges). It does not identify the executable that Foundry is running. Every `azd deploy` creates a new immutable Foundry version, even for the same logical version, and each environment's project numbers versions independently. In this run, scanner `1.2.0` was Foundry version `1` and scanner `1.2.1` was Foundry version `2`. Only the agent name plus the Foundry version pins the deployed code, configuration, and environment variables.

2. **Why capture an immutable version endpoint and use a version-bound session?** Invoking a logical agent name serves whatever version is current when the call arrives. A deploy in the middle of a canary would silently change what the stable or rolled-back path calls. Creating the session with `version_indicator.version_ref` and rejecting a mismatched returned version (`served_version` / `x-ms-agent-version`) proves that the orchestrator, dashboard, and smoke evaluation exercised exactly the version recorded in `release-set.json`.

3. **Why does the orchestrator deploy after scanner and reviewer?** The specialists are independent of each other, but the orchestrator is not. Its environment (`SCANNER_/REVIEWER_RESPONSES_ENDPOINT`, `_AGENT_NAME`, `_AGENT_VERSION`) needs their immutable outputs, which exist only after their deploys finish. The deploys are also serial because they share one selected azd environment state file, and concurrent deploys would race on it.

4. **Why is the dashboard, not Foundry, the 75/25 traffic boundary?** Foundry hosted agents expose immutable versions and version-bound sessions, but the lab does not claim native weighted routing across agent versions. Container Apps has authoritative, auditable revision weights and labels. Each dashboard revision is pinned to one orchestrator version, so weighting dashboard revisions exposes the stable and candidate release sets without misrepresenting what Foundry does.

5. **How do direct label URLs make canary verification deterministic?** The weighted URL is random per request, so a short sample proves nothing. The `stable` and `candidate` label hostnames always route to one specific revision. In Azure, the label hostname is `<app>---<label>.<env-domain>`, for example `fabrikam-release-lab09-cicd-d---stable...`. Repeated calls must therefore always return that revision's release-set ID and orchestrator version, and the pipeline asserts this.

6. **Why can't rollback assume the second-newest revision is safe?** Revision age says nothing about verification. The previous revision may itself have been a failed candidate, a bootstrap image, a hotfix that never passed evaluation, or (as in this run) a revision with bad configuration. Rollback must use the persisted `verified-<env>` manifest, which names the exact revision and the exact Foundry versions that passed smoke, label, and invocation checks.

7. **Why does reverse-dependency closure include the orchestrator when the scanner fails?** The orchestrator version is bound to specific scanner and reviewer versions through its environment variables. Restoring only the scanner would leave the current orchestrator calling the failed scanner version. The closure is computed in reverse dependency order, which yields `orchestrator, scanner`. It restores the whole compatible set, which here means the dashboard revision that targets the verified orchestrator, which in turn targets the verified scanner.

8. **Which fields are identical across staging and production, and which may differ?** These must be identical: source commit, `reviewed_release_id`, logical versions, dependency ranges, contract digest, model policy (`gpt-5.4-mini` / `2026-03-17`), hosted manifests, and evaluation dataset/evaluator identity. These may differ: Foundry project/account and endpoints, immutable Foundry agent version numbers, `release_set_id` (it includes the environment and versions), dashboard app name/revision/FQDN/label URLs, and the resource group.

9. **Why are the healthy/regression fixtures secondary?** They are static numbers used to exercise the promote/hold/rollback policy branches deterministically. They don't observe the deployed agents. The primary evidence is the version-bound smoke evaluation, which is tied to the source commit, release-set ID, and exact orchestrator version. Promotion is refused without it.
   *Observation from this run:* the shipped evaluator records `passed` for any non-empty response. When the orchestrator's identity lacked RBAC to call the specialists, it still returned a non-empty "unable to assess" JSON and the smoke "passed". A stronger evaluator should assert the `coordinate_review` contract fields and specialist success.

10. **Which managed identity invokes Foundry from the dashboard, and why is no API key needed?** The dashboard Container App's **system-assigned managed identity**. Bicep grants it **Azure AI User** (`53ca6127-...`) on the Foundry project and **AcrPull** on the registry. `DefaultAzureCredential` obtains an Entra token for `https://ai.azure.com/.default`, and hosted-agent session/Responses endpoints accept Entra bearer tokens, so no stored key exists to leak or rotate. Likewise, the hosted orchestrator calls the specialists with its own agent instance identity, which needs Azure AI User on the project as well.
